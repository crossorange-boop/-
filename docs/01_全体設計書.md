## 1. アーキテクチャ

```
[スマホ / PC ブラウザ]
        │  HTTPS（Googleアカウント認証）
        ▼
┌──────────── Google Apps Script Webアプリ ────────────┐
│ UI層        index.html + css + js（SPA・レスポンシブ）   │
│   │ google.script.run                                    │
│ API層       Api.gs  ── 認可チェック・入力検証・例外整形   │
│   │                                                      │
│ サービス層  ProjectService / TaskService / AgentService  │
│             DeliverableService / ApprovalService         │
│             NotificationService / ScheduleService        │
│   │                                                      │
│ エンジン層  StateMachine（状態遷移ルール）               │
│             AssignmentEngine（ルールベース割り振り）     │
│             QueueEngine / DeadlineEngine / RecoveryEngine│
│   │                                                      │
│ アダプター層 AgentAdapter（共通IF）                       │
│             ├ ManualQueueAdapter（Phase1：作業待ちキュー）│
│             └ 将来：N8nAdapter / ClaudeCodeAdapter …     │
│   │                                                      │
│ データアクセス層 Repository（共通IF）                     │
│             └ SheetsRepository（Phase1）                 │
│               将来：PostgresRepository（JDBC等）へ差替可 │
└──────────────────────────────────────────────────────────┘
        ▼                         ▼
 [Google Sheets：DB]       [Google Drive：成果物・バックアップ]

[時間主導型トリガー] → Jobs.gs → エンジン層（PC不要・Google側で実行）
```

設計原則
- **UIはビジネスロジックを持たない**。すべてAPI層経由。
- **サービス層はSheetsを直接触らない**。必ず Repository 経由（DB移行に備える）。
- **エンジン層は純粋関数中心**（入力：データ配列 → 出力：変更指示）。Node上で単体テスト可能にする。
- **特定AIに依存しない**。AIは Agents シートのデータ＋アダプターとして扱い、統括は Rule Engine（GAS自身）が行う。
- **データは物理削除しない**（論理削除＋監査ログ）。

## 3. データ構造（Google Sheets）

### 3.1 共通ルール
- ID形式：`PRJ-` `TSK-` `AGT-` `DLV-` `DEP-` `EXE-` `APR-` `NTF-` + `yyyyMMddHHmmss` + 4桁ランダム（人が読めて衝突しにくい）
- 日時：ISO 8601（Asia/Tokyo）文字列で保存
- 複数値（capabilities、dependency_task_ids）：カンマ区切り
- 1行目＝ヘッダー。**列はヘッダー名で参照**（列の並び替え・追加で壊れない）
- 書き込みは必ず `LockService.getScriptLock()` 内で実行

### 3.2 指示書の9シート（指定どおり）

指定された列はすべてそのまま作成します。加えて、要件（重複実行防止・論理削除・自動割り振り・楽観ロック）を満たすため、**以下の追加列を提案します**（各シート末尾に追加。指定列は変更しません）。

| シート | 指定列 | **追加提案列** | 追加理由 |
| --- | --- | --- | --- |
| ① Projects | 指示書どおり | `goal`, `is_deleted`, `row_version` | 目標設定、論理削除、同時編集の衝突検知 |
| ② Tasks | 指示書どおり | `category`, `required_capability`, `instruction`, `reference_urls`, `waiting_reason`, `lock_token`, `locked_until`, `is_deleted`, `row_version` | 自動分類・割り振り、AIへの指示書と資料、WAITING理由、重複実行防止、論理削除 |
| ③ Agents | 指示書どおり | `priority`, `max_concurrent_tasks`, `last_status_changed_at`, `row_version` | 候補が複数いる場合の優先度、同時担当上限、復旧検知 |
| ④ Deliverables | 指示書どおり | `is_deleted` | 論理削除 |
| ⑤ Dependencies | 指示書どおり | — | dependency_type：`FS`（完了→開始）を初期値。将来 SS/FF 対応 |
| ⑥ ExecutionLogs | 指示書どおり | `triggered_by` | 手動／トリガー／API の区別 |
| ⑦ Approvals | 指示書どおり | `target_type`, `target_id`, `payload_json` | 承認後に実行する操作内容を保持 |
| ⑧ Settings | 指示書どおり | — | 下記 3.4 |
| ⑨ Notifications | 指示書どおり | `severity` | INFO / WARN / CRITICAL |

`dependency_task_ids`（Tasks）と Dependencies シートの二重管理について：**正は Dependencies シート**とし、Tasks.dependency_task_ids は表示用キャッシュとして同時更新します。

### 3.3 追加提案シート（2枚）

## 4. タスク状態遷移

```
BACKLOG ──分類・割振──▶ READY ──担当決定──▶ ASSIGNED ──着手──▶ IN_PROGRESS ──成果物提出──▶ REVIEW ──▶ APPROVAL ──承認──▶ COMPLETED
   │                     ▲  │                 │                   │                         │差戻し      │差戻し
   │依存未完了            │  │AI利用不可        │AI利用不可          │エラー                    ▼            ▼
   └──▶ BLOCKED ─依存完了─┘  └──▶ WAITING ──AI復旧──▶ READY     └──▶ FAILED ─再実行(上限内)─▶ READY   IN_PROGRESS
任意の未完了状態 ──▶ CANCELLED（人間操作のみ・理由必須）
```

- 遷移ルールは `StateMachine` に表として一元定義し、表にない遷移はすべて拒否。
- **WAITING / BLOCKED / FAILED でもタスク行は削除しない**。`waiting_reason` に理由を記録。
- REVIEW → APPROVAL は、Approvals 対象の操作を含むタスク（または設定で承認必須にしたプロジェクト）のみ経由。

## 5. 自動管理エンジン（時間主導型トリガー）

| トリガー | 初期間隔 | 処理 |
| --- | --- | --- |
| jobQueueCheck | 5分 | ①BACKLOGを AssignmentRules で分類 ②依存確認（未完了→BLOCKED、完了→READY） ③担当AIの稼働確認（不可→WAITING） ④WAITINGのうち担当AIが復旧したものを READY に戻す ⑤優先度・期限順に並べ、担当AI別作業待ちキューへ ASSIGNED |
| jobDeadlineCheck | 15分 | 期限接近・超過の検出、後続タスクへの影響（依存チェーン）算出、再調整案（後続の開始/期限をずらす案）を通知として作成 ※自動では書き換えず、人が採用 |
| jobDailyPlan | 毎朝 7時 | 当日のタスク一覧を通知に作成 |
| jobMiddayCheck | 毎日 13時 | 中間経過を通知に作成（本日完了・今日期限の残り・期限超過・午後に優先するタスク・止まっているタスク・承認待ち） |
| jobDailySummary | 毎夕 17時 | 進捗集計を通知に作成 |
| jobBackup | 毎日 3時 | スプレッドシートを Drive のバックアップフォルダへ複製、保持世代を超えた古いものはゴミ箱へ |

**重複実行防止（二重の仕組み）**
1. ジョブ全体：`LockService.tryLock()` を取れなければ即終了（前回処理がまだ動いている場合）。
2. タスク単位：`lock_token` と `locked_until` で同一タスクの二重処理を防止。期限切れロックは自動解除。

**無料枠への配慮**
- 1回の処理は `JOB_TIME_BUDGET_SEC` で打ち切り、残りは次回へ持ち越し。
- シートは1回の処理で一括読み込み・一括書き込み（API呼び出し回数を最小化）。
- 間隔は Settings で変更 → 画面の「トリガー再設定」で反映。
- 日次トリガーは Google の仕様上、指定時刻から最大±15分程度ずれて実行される。
- 参考：一般Googleアカウントのトリガー合計実行時間は1日90分。5分間隔×288回/日なので、1回あたり平均約18秒以内に収める設計（実測値は ExecutionLogs で確認可能）。Google Workspace アカウントは上限が緩くなります。

## 6. ルールベース自動割り振り

1. タスク名・説明・カテゴリを AssignmentRules（priority順）と照合 → `category` と `required_capability` を決定
   - 例：「開発|プログラム|GAS|バグ」→ development → Claude Code
   - 「Instagram|インスタ|SNS|投稿」→ sns → Muse
   - 「デザイン|バナー|資料|スライド」→ design → Canva
   - 「分類|整理|定型|集計」→ classification → Rule Engine
2. 候補エージェント＝ `enabled=TRUE` かつ capabilities に required_capability を含む
3. スコア：availability（AVAILABLE優先）→ usage_limit_status → 現在の担当件数（max_concurrent_tasks 以内）→ Agents.priority
4. 候補なし／全員利用不可 → `WAITING`（理由記録）。ルール不一致 → BACKLOGのまま「要手動分類」通知。
5. **外部AIへのAPI呼び出しは行わない**。ASSIGNED タスクは「担当AI別 作業待ちキュー」画面に表示され、指示書（instruction）と資料リンクをコピーして各AIに手動で渡す運用。成果物は Drive リンクで登録。

## 8. デプロイ方式（要選択）

| 方式 | 内容 | 長所 | 短所 |
| --- | --- | --- | --- |
| **A. clasp（推奨）** | ユーザーのPCで一度 `clasp login` し、`clasp push` で反映 | 更新が確実・差分管理できる | 初回にPCでのコマンド操作が必要（無料） |
| B. 手動コピー | Apps Script エディタにファイルを貼り付け | ツール不要 | ファイル数が多く更新時に手間・ミスが起きやすい |

いずれの方式でも、**実際のGoogleアカウントへの反映・Webアプリ公開はユーザー承認後**に行います。認証情報（`.clasprc.json` 等）はリポジトリに含めません（`.gitignore` で除外）。

## 9. セキュリティ設計

| 要件 | 実装 |
| --- | --- |
| アクセス制限・Google認証 | Webアプリ「アクセス：自分のみ」（Workspaceなら「ドメイン内」も可）＋ `ALLOWED_USERS` による二重チェック |

| 重要操作の承認制 | APPROVAL_REQUIRED_ACTIONS に該当する操作は Approvals に登録し、承認後のみ実行。Phase 1 ではメール送信機能自体を持たない（通知は画面内） |
| 定期バックアップ | 毎日 Drive へ複製、14世代保持。復旧手順を文書化 |
| OAuthスコープ | 必要最小限（spreadsheets・drive.file 相当・script.scriptapp）を appsscript.json に明示 |

## 10. テスト方針

- **Node単体テスト**（このコンテナで実行）：StateMachine の全遷移、AssignmentEngine のルール照合・スコアリング、依存判定、期限判定、WAITING⇔復旧。モックRepositoryを使用。
